ftx-crash: reading the code

What this project does, how the pieces fit together, and the things you need to know before you trust a number that comes out of it.

How to use this

Sections follow execution order. Every snippet is copied from the files under src/ftx_crash/ and scripts/. Coloured boxes flag design choices, traps and honest weaknesses. Every number in a Sample data box was printed by running this project's own code on this project's own parquet files — nothing on this page is invented. Where the code could not be run, the page says so instead of guessing.

The process in plain English

The project compares two crypto blow-ups of 2022 — the Terra/LUNA collapse in May and the FTX exchange failure in November — by measuring how far the futures price drifted away from the spot price during each one. It loads minute-by-minute Bitcoin prices and futures prices, works out an annualised gap ("basis") for every minute, subtracts each crisis's own calm-period average to get an "abnormal" gap, and then runs statistical tests to ask whether the FTX dislocation was bigger, more volatile and longer-lasting than the LUNA one. It answers yes on all three counts, and then adds five further robustness layers from the RiskLabAI library. Section 10 explains why that headline answer should not be believed as stated.

In plain words

main reads two optional switches, hands any overrides to the pipeline, and optionally prints the names of every variable the run left behind.

What it does

Input: command-line arguments. Output: nothing returned; side effects are PNG charts in outputs/figures/ and CSV tables in outputs/tables/. Role: the only supported user interface.

Trap

--smoke currently does nothing. SMOKE_OVERRIDES is an empty dictionary, so passing the flag produces exactly the same full-length run. The one override any step reads is max_uniqueness_events in step 17, and nothing sets it. If you want a fast run, you have to put that key into SMOKE_OVERRIDES yourself.

02The execution model — pipeline.py and config.py

This is the single most important idea in the project. The code began life as one long Jupyter notebook. Rather than rewrite it into functions and modules, the author split the notebook into nineteen files and kept notebook semantics: one shared dictionary of global variables that every file reads from and writes to.

def run_pipeline(context_overrides: dict[str, Any] | None = None) -> dict[str, Any]:
    """Run each step script in sorted filename order with a shared global context.

    Returns the final execution namespace (all globals produced by the steps).
    """
    config = ProjectConfig()
    context = build_execution_context(
        config=config, context_overrides=context_overrides
    )

    for step_path in sorted(config.steps_dir.glob("*.py")):
        context["__file__"] = str(step_path)
        source = step_path.read_text()
        exec(compile(source, str(step_path), "exec"), context)

    return context
In plain words

It finds every .py file in the steps folder, sorts them by name, and runs each one inside the same bag of variables, so anything file 03 creates is still there when file 17 runs.

What it does

Input: an optional dictionary of overrides. Output: the final namespace, a dictionary holding every variable the nineteen files created (roughly 200 keys). Role: the engine. Nothing else in the project loops over the steps.

Why it is written this way

The stated goal in GUIDE_src.md is notebook parity: keep the converted code close enough to the original notebook that a reader can compare them side by side. A shared exec namespace reproduces notebook behaviour exactly, including the parts of notebook behaviour that are bad ideas.

Trap

Because the files share one namespace, an import in file 01 is what makes np exist in file 08. A tool that removes "unused" imports from a single file will happily delete an import that four other files depend on, and nothing will catch it until the run crashes. That is exactly what had happened to this working tree — see Fixes applied.

Trap

The order is sorted filename order, not the order in the split map. It works only because every file is prefixed with a zero-padded two-digit number. Add a file called 20_extra.py and it runs last, as expected; add 9_extra.py and it runs after 19_..., because "9" sorts after "1".

build_execution_context — makes the folders and seeds the namespace

def build_execution_context(
    config: ProjectConfig,
    context_overrides: dict[str, Any] | None = None,
) -> dict[str, Any]:
    """Build the shared global namespace used when executing step scripts."""
    config.processed_data_dir.mkdir(parents=True, exist_ok=True)
    config.figures_dir.mkdir(parents=True, exist_ok=True)
    config.tables_dir.mkdir(parents=True, exist_ok=True)

    overrides = dict(context_overrides or {})
    smoke_test_mode = bool(overrides.get("SMOKE_TEST_MODE", False))

    context: dict[str, Any] = {
        "__name__": "__main__",
        "PROJECT_ROOT": config.project_root,
        ...
        "OVERRIDES": overrides,
        "SMOKE_TEST_MODE": smoke_test_mode,
    }
    context.update(overrides)
    return context
What it does

Input: a ProjectConfig and optional overrides. Output: a dictionary holding six path variables plus the override bag. Role: gives the step files their only knowledge of where anything lives on disk.

Why paths are derived, not hard-coded

ProjectConfig.project_root is Path(__file__).resolve().parents[2]. The file sits at src/ftx_crash/config.py, so two levels up is the project root. Every other path hangs off that. The run therefore works from any working directory, which matters because the notebook, the console script and the wrapper script all start from different places.

The weakness, stated honestly

context.update(overrides) writes every override key straight into the global namespace. An override named data or plt would silently shadow the panel or the plotting library. There is no allow-list and no validation.

The date filters live in the conversion script, not in the analysis. Bitcoin spot starts on 2022-04-01 and BITO starts on 2022-10-01, but step 04 declares estimation windows starting 2022-03-01 and 2022-09-01. The declared windows are silently truncated by the data. See Edge cases.

Step 04 — the event windows

Why the windows are split this way

This is the standard shape of an event study. The estimation window is a calm period used to work out what "normal" looks like; the crisis window is the period under test; the post-crisis window is used to measure how long it took to return to normal. Because the estimation window ends the day before the crisis window starts, the benchmark never uses information from the crisis itself — there is no look-ahead bias in this part of the design.

05The basis and the panel — steps 05 and 06

calculate_basis — annualised gap between futures and spot

def calculate_basis(futures_price, spot_price, days_to_maturity):
    """Annualized futures basis in percent: ((F - S) / S) * (365 / T) * 100.

    Parameters
    ----------
    futures_price, spot_price
        Price series (aligned index).
    days_to_maturity
        Calendar days until contract expiry; floored at 1 to avoid division by zero.
    """
    days_to_expiry = np.maximum(days_to_maturity, 1)
    return ((futures_price - spot_price) / spot_price) * (365 / days_to_expiry) * 100
In plain words

Work out how much dearer the futures contract is than the spot price, as a percentage, then scale it up to what that would be worth over a full year.

What it does

Input: two aligned price series and a count of calendar days to expiry. Output: a series of annualised percentages. Role: the single measurement the whole study is built on. Everything after this point is arithmetic on its output.

The formula

$$b_t \;=\; \frac{F_t - S_t}{S_t}\;\times\;\frac{365}{\max(T_t,\,1)}\;\times\;100$$

$b_t$ is the annualised basis in per cent at minute $t$. $F_t$ is the futures price, $S_t$ the spot price. $T_t$ is the number of whole calendar days from minute $t$ to the contract's expiry date; the $\max(\cdot,1)$ stops the division blowing up on and after expiry day. The factor $365$ turns a gap earned over $T_t$ days into a yearly rate, and $100$ turns a fraction into per cent.

Sample data

spot   S = 30191.82
futures F = 30824.00
expiry     2022-06-24
days    T = 45

               annualised to about 17%

(30824.00 − 30191.82) / 30191.82 = 0.020939; 0.020939 × 365/45 × 100 = 16.9837.

This is the finding that matters most on this page. A BITO share costs about \$2.66; one Bitcoin costs about \$17,663. Their ratio is almost exactly zero, so $(F-S)/S$ is almost exactly $-1$ at every minute, and the "basis" is really just $-100 \times 365 / T$ — a function of the calendar, not of the market. See section 10.

In plain words

Build one table for the LUNA period and one for the FTX period, each on a one-minute clock, then stack them on top of each other into a single table called data that every later step slices.

What it does

Input: the three frames from step 03 plus two hourly quarterly-futures files. Output: data, 260,428 rows by 14 columns, one-minute UTC index. Role: the one object the rest of the project reads.

The formula

$$\text{slope}_t \;=\; b^{\,\text{Sep}}_t - b^{\,\text{Jun}}_t$$

$b^{\,\text{Jun}}_t$ is the annualised basis of the June contract at minute $t$, $b^{\,\text{Sep}}_t$ the same for the September contract. The difference is the term-structure slope: how much more (or less) the market pays for holding the exposure three months longer.

06Abnormal basis and persistence — steps 07 and 08

Step 07 — subtract the calm-period average

luna_est_data = data.loc[luna_estimation_start:luna_estimation_end]
luna_normal_front_basis = luna_est_data["luna_front_basis"].mean()
...

The formula

$$\bar b^{\,\text{est}} \;=\; \frac{1}{N_{\text{est}}}\sum_{t \in \text{estimation}} b_t \qquad\qquad a_t \;=\; b_t - \bar b^{\,\text{est}}$$

$b_t$ is the annualised basis at minute $t$. $\bar b^{\,\text{est}}$ is its average over the estimation window only, with $N_{\text{est}}$ the number of minutes in that window. $a_t$ is the abnormal basis: how far this minute sits from what was normal before the crisis began. This is the event-study residual, using a constant-mean benchmark rather than a market model.

Why this is free of look-ahead bias

The benchmark is computed on luna_est_data, which ends on 8 May, and applied to a crisis starting 9 May. No crisis observation contributes to the number it is measured against. This is the one place in the project where the timing discipline is clearly right.

The weakness, stated honestly

A negative "normal basis" of −524.62 per cent is not a market fact; it is the average of the BITO-versus-Bitcoin artefact described in section 05. Subtracting it removes the constant part of the artefact but leaves the part that varies with days-to-expiry.

calculate_half_life — how fast the dislocation faded

# The panel built in step 06 is 1-minute data, so an AR(1) fitted on consecutive
# rows gives a half-life counted in bars (minutes). Downstream steps print the
# half-life in hours and divide by 24 for days, so convert here.
BARS_PER_HOUR = 60


def calculate_half_life(series, bars_per_hour: float = BARS_PER_HOUR) -> float:
    clean_series = series.dropna()
    if len(clean_series) < 10:
        return np.nan

    y = clean_series.values[1:]
    y_lag = clean_series.values[:-1]

    # OLS estimate of rho (no intercept since abnormal basis is demeaned)
    rho = np.sum(y * y_lag) / np.sum(y_lag**2)

    # Handle edge cases
    if rho >= 1:  # Non-stationary (unit root or explosive)
        return np.inf
    elif rho <= 0:  # Negative autocorrelation (oscillatory)
        return np.inf  # Half-life undefined for negative rho

    half_life_bars = -np.log(2) / np.log(rho)
    return half_life_bars / bars_per_hour
In plain words

Measure how strongly each minute's dislocation carries into the next minute, then convert that into "how long until half of it has gone".

What it does

Input: a post-crisis abnormal-basis series on the one-minute grid. Output: one number, the half-life in hours (or infinity when the fit says the dislocation never decays). Role: the "persistence" leg of the project's three-dimensional comparison.

The formula

The model fitted is a first-order autoregression through the origin:

$$a_t \;=\; \rho\, a_{t-1} + \varepsilon_t$$

The least-squares estimate with no intercept is the ratio of the cross-product to the sum of squared lags:

$$\hat\rho \;=\; \frac{\sum_{t=2}^{N} a_t\,a_{t-1}}{\sum_{t=2}^{N} a_{t-1}^{2}}$$

Repeated $k$ times, the expected level is $\rho^{k} a_t$. Setting that to half and taking logarithms gives the half-life in bars, which the code divides by 60 to get hours:

$$H \;=\; \frac{-\ln 2}{\ln \hat\rho}\;\Big/\;60$$

$a_t$ is the abnormal basis at minute $t$; $\varepsilon_t$ is the unexplained part of that minute; $\hat\rho$ is the estimated carry-over from one minute to the next, between 0 and 1 for a decaying series; $N$ is the number of minutes in the post-crisis window; $H$ is the half-life in hours; the 60 is BARS_PER_HOUR, the number of one-minute bars in an hour.

Sample data

def cohens_d(x1, x2):
    """Calculate Cohen's d effect size."""
    n1, n2 = len(x1), len(x2)
    var1, var2 = np.var(x1, ddof=1), np.var(x2, ddof=1)
    pooled_std = np.sqrt(((n1 - 1) * var1 + (n2 - 1) * var2) / (n1 + n2 - 2))
    return (np.mean(x1) - np.mean(x2)) / pooled_std


basis_cohens_d = cohens_d(ftx_ab_basis, luna_ab_basis)
did_estimate = ftx_avg_abnormal_basis - luna_avg_abnormal_basis
In plain words

Ask three questions: are the two averages different (t-test), are the two distributions different (Mann-Whitney), and how big is the gap relative to the spread (Cohen's d)?

The formula

Welch's t-statistic, which does not assume the two groups have the same spread:

$$t \;=\; \frac{\bar x_1-\bar x_2}{\sqrt{\dfrac{s_1^{2}}{n_1}+\dfrac{s_2^{2}}{n_2}}}$$

Cohen's d, the same gap measured in pooled standard deviations:

$$d \;=\; \frac{\bar x_1-\bar x_2}{s_p}, \qquad s_p \;=\; \sqrt{\frac{(n_1-1)s_1^{2}+(n_2-1)s_2^{2}}{n_1+n_2-2}}$$

The difference-in-differences estimator, which here is simply the gap between the two average abnormal bases:

$$\delta_{\text{DiD}} \;=\; \bar a^{\,\text{FTX}} - \bar a^{\,\text{LUNA}}$$

$\bar x_i$ is group $i$'s mean, $s_i^{2}$ its sample variance, $n_i$ its size. $s_p$ is the pooled standard deviation. $\bar a^{\,\text{FTX}}$ and $\bar a^{\,\text{LUNA}}$ are the average abnormal basis over each crisis window. Group 1 is FTX and group 2 is LUNA in the cohens_d call, which is why $d$ comes out negative.

In plain words

Take the first six minutes of each crisis, boil them down to four numbers, then build a fake training set by adding random noise around those numbers and train a random forest to tell the two crises apart.

What it does

Input: the crisis-window slice of data. Output: four features per crisis, then 100 noisy copies of each, then a fitted RandomForestClassifier and a feature-importance table. Role: the project's "early warning" claim.

The formula

Each synthetic sample is the real feature plus Gaussian noise scaled to the feature's own size:

$$x^{(i)}_j \;=\; x_j \;+\; \varepsilon^{(i)}_j, \qquad \varepsilon^{(i)}_j \sim \mathcal{N}\!\left(0,\;\bigl(\sigma\,|x_j| + \epsilon_0\bigr)^{2}\right)$$

Step 15 — the CUSUM filter

The formula

The symmetric cumulative-sum filter keeps two running totals and fires an event when either crosses a threshold, then resets both:

$$S^{+}_t=\max\bigl(0,\;S^{+}_{t-1}+\Delta y_t\bigr), \qquad S^{-}_t=\min\bigl(0,\;S^{-}_{t-1}+\Delta y_t\bigr)$$

An event is recorded at time $t$ when $S^{+}_t \ge h_t$ or $S^{-}_t \le -h_t$, and whichever total fired is set back to zero.

$\Delta y_t$ is the change in the price series from $t-1$ to $t$. $S^{+}$ accumulates upward moves, $S^{-}$ downward ones. $h_t$ is the threshold, which this code makes time-varying: daily_volatility_with_log_returns(prices, span=100) gives a rolling volatility as a fraction, and multiplying it by the price converts it into currency units.

Why the timezone is stripped and put back

Lines 6 to 12 of step 15 remove the UTC label before calling RiskLabAI and re-apply it afterwards, with the comment "RiskLabAI compatibility fix for Timezones". The library does not handle timezone-aware indexes, so the code works around it rather than patching the library. The re-localisation assumes the naive timestamps were UTC, which they were.

Step 16 — fractional differentiation

The formula

Ordinary differencing subtracts yesterday from today and throws away the level. Fractional differencing applies a non-integer power of the backshift operator, which removes the trend more gently:

$$\tilde y_t \;=\; \sum_{k=0}^{K} \omega_k \, y_{t-k}, \qquad \omega_0 = 1, \qquad \omega_k \;=\; -\,\omega_{k-1}\,\frac{d-k+1}{k}$$

$y_t$ is the original series, $\tilde y_t$ the differenced one. $d$ is the differencing degree: $d=0$ leaves the series untouched, $d=1$ is ordinary first differencing. $\omega_k$ is the weight on the observation $k$ steps back, built by the recursion shown. $K$ is where the weights are cut off once they become negligible. The code searches over $d$ and keeps the smallest one that passes the augmented Dickey-Fuller stationarity test at the five per cent level, which is the value that keeps the most memory.

Why the series is shifted before differencing

The RiskLabAI routine takes logarithms internally, and logarithms need positive inputs. The basis goes deeply negative, so lines 19 and 20 add abs(global_min) + 100 to every value first. The comment says the buffer is 100 per cent.

Trap

Step 18 reuses shift_val — a number calibrated on the raw basis — on the abnormal basis. The two series have different minima, so the shift is not guaranteed to make the abnormal series positive, and the comment in step 18 says only "use the SAME shift_val".

Step 17 — sample uniqueness weights

The formula

Two observations that both span the same stretch of time carry overlapping information. Concurrency counts how many observations are live at each instant, and an observation's weight is the average of the reciprocal concurrency over its own life:

$$c_t \;=\; \sum_{i=1}^{N} \mathbf{1}_{\{t \in [t_{i,0},\, t_{i,1}]\}}, \qquad u_i \;=\; \frac{1}{|I_i|}\sum_{t \in I_i} \frac{1}{c_t}$$

$N$ is the number of events. $[t_{i,0}, t_{i,1}]$ is the interval event $i$ spans, from its observation minute to the contract's expiry. $\mathbf{1}_{\{\cdot\}}$ is 1 when the condition holds and 0 otherwise, so $c_t$ is simply how many events are live at time $t$. $I_i$ is the set of time steps inside event $i$ and $|I_i|$ its size. $u_i$ lands between 0 and 1: close to 1 when the event is alone, close to 0 when it overlaps heavily. The weights are then rescaled so they sum to $N$.

Why the event count is capped

create_indicator_matrix builds a table with one row per minute and one column per event. At 1,000 events over roughly 70,000 minutes that is already about 70 megabytes of unsigned bytes. Without the max_uniqueness_events = 1000 cap and the even sampling in reduce_event_count, the full 70,000 events would need a matrix around seventy times larger.

The weakness, stated honestly

The weights are computed but never fed back into the tests in step 09. Step 17 prints a weighted mean beside the unweighted one and stops there. The headline p-values on the page are still the unweighted ones.

Step 18 — the backdoor regression

The formula

$$\tilde a_t \;=\; \beta_0 \;+\; \beta_1 \, D_t \;+\; \beta_2 \, \sigma_t \;+\; \beta_3 \ln P_t \;+\; u_t$$

$\tilde a_t$ is the fractionally differenced abnormal basis. $D_t$ is the crisis indicator: 0 for a LUNA-window minute, 1 for an FTX-window minute. $\sigma_t$ is the rolling 24-bar standard deviation of returns multiplied by $\sqrt{24}$. $\ln P_t$ is the natural logarithm of the Bitcoin price. $u_t$ is the residual. $\beta_1$ is the quantity the step reports: the FTX effect after holding volatility and price level fixed. The name "backdoor adjustment" comes from causal inference and means blocking the paths through the confounders — here, the market regime.

Trap

The volatility control multiplies by $\sqrt{24}$, which annualises correctly only for hourly data. The panel is one-minute data, so the scaling factor is wrong. Because the same wrong factor is applied to both crises, the regression coefficient $\beta_2$ absorbs it and $\beta_1$ is unaffected — but the printed value of $\beta_2$ is not in the units its name implies.

Step 19 — synthetic robustness

The formula

The simulated market is a Heston stochastic-volatility model with Merton jumps, run under two regimes that switch according to a Markov chain:

$$dS_t = \mu S_t\,dt + \sqrt{v_t}\,S_t\,dW^{S}_t + S_t\,dJ_t$$

$$dv_t = \kappa\,(\theta - v_t)\,dt + \xi\sqrt{v_t}\,dW^{v}_t, \qquad \mathrm{corr}\bigl(dW^{S}_t, dW^{v}_t\bigr) = \rho$$

$S_t$ is the simulated price and $v_t$ its instantaneous variance. $\mu$ is the drift, calibrated from each crisis's own mean return. $\kappa$ is how fast variance pulls back to its long-run level $\theta$, which is set to the crisis's squared annualised volatility. $\xi$ is the volatility of variance and $\rho$ the correlation between the two random drivers, set to $-0.7$ and $-0.8$ so that prices falling and volatility rising go together. $dJ_t$ is a jump term firing at rate $\lambda$ with mean size $m$ and variance $v$. The transition matrix is $\begin{pmatrix}0.95 & 0.05\\ 0.05 & 0.95\end{pmatrix}$, so each step has a five per cent chance of switching regime.

Why there is a fallback

The whole generation call sits inside try. If RiskLabAI raises anything, the code prints the error and falls back to bootstrap resampling of the real crisis returns. That keeps the run alive, and the failure is printed rather than hidden — but the printed conclusion at the end does not say which path produced the numbers.

Trap

The fallback calls np.random.random() with no seed of its own. It inherits whatever seed state step 13 left behind, so the fallback path is reproducible only by accident.

10What the numbers actually mean

The central problem, stated first

The FTX side of the comparison does not measure a futures basis. The formula $(F-S)/S$ requires $F$ and $S$ to be prices of the same underlying quantity. On the FTX leg, $F$ is the share price of the BITO exchange-traded fund (about \$2.66) and $S$ is the price of one Bitcoin (about \$17,663). One BITO share is not one Bitcoin; it is a small claim on a futures-rolling strategy. So $(F-S)/S$ is approximately $-1$ at every single minute, and the "annualised basis" reduces to $-100 \times 365/T$, a smooth function of days to expiry.

What would make the comparison sound

Three changes, in order of importance. First, compare like with like: use the Binance December 2022 quarterly Bitcoin contract against Bitcoin spot for the FTX window, the same way the LUNA window uses the June contract — or, if BITO must be used, convert it to a Bitcoin-equivalent exposure per share first. Second, drop the days after contract expiry rather than clamping $T$ at 1, which alone removes 10,080 rows whose standard deviation is eighteen times the rest of the sample. Third, stop treating consecutive minutes as independent: use the uniqueness weights that step 17 already computes, or aggregate to a coarser bar and use standard errors robust to autocorrelation.

What survives

The LUNA leg is built correctly: Bitcoin spot against a Binance Bitcoin quarterly future, both in US dollars, on the same clock. Its numbers before the June expiry are meaningful — a mean basis of about 2.7 per cent annualised, dropping to −64 per cent at the worst minute of the May crisis. The event-study machinery around it (estimation window, abnormal series, half-life) is also correctly wired. What fails is the comparison, not the framework.

16If they point at a line

QuestionAnswer
"Why exec instead of imports?"To keep notebook semantics. The nineteen files share one namespace exactly as nineteen notebook cells would, which lets a reader compare each file against the original notebook in docs/reference/ftx-crash.ipynb.
"Where is look-ahead bias prevented?"Step 07. The benchmark average comes from luna_est_data, which ends the day before the crisis window opens, so no crisis observation influences the number it is compared against.
"Is there look-ahead bias anywhere?"Yes, in step 18. The differencing degree $d$ is chosen in step 16 using the estimation, crisis and post-crisis periods together, then applied to the crisis window. The transformation is fitted with knowledge of the period it is applied to.
"Why is the half-life 5.8 hours and not 348?"Because the fit is on one-minute bars, so it produced 348 minutes. Step 08 now divides by BARS_PER_HOUR. See Fixes applied.
"Why is the FTX half-life infinite?"The estimated one-lag coefficient fell outside the open interval from 0 to 1, so the function returns np.inf by design rather than reporting a negative or undefined half-life.
"What happens if I change the crisis window in step 04?"Everything downstream moves: the benchmark average, both abnormal series, all three tests, the classifier features and the causal regression. Nothing is cached, so a rerun is enough.
"Why does the FTX basis barely move minute to minute?"Because it is not measuring a basis. A \$2.66 exchange-traded fund share is being compared with a \$17,663 Bitcoin, so the ratio is pinned near −1 and the series follows the days-to-expiry calendar. See section 10.
"How long does a full run take?"Steps 01 to 13 take a few minutes on the bundled data. Steps 15 and 17 are the slow ones: the CUSUM filter walks 260,428 rows in Python, and the uniqueness matrix is about 70 megabytes per crisis. Steps 14 to 19 could not be timed, because the dependency will not install.
"Why is --smoke there if it does nothing?"It is scaffolding. SMOKE_OVERRIDES is empty, so the flag has no effect today. Putting {"max_uniqueness_events": 50} into it would make it real.
"Which tables are trustworthy?"tab_appendix_event_timeline overstates the estimation windows. tab1, tab2 and tab4 are each written twice under near-identical names, once in steps 06 to 13 and again in step 19. Only the LUNA columns rest on a correctly constructed basis.

18Limitations, stated honestly

  • The FTX basis is not a basis. Comparing a \$2.66 fund share with a \$17,663 Bitcoin makes the series a function of days to expiry. Every FTX-versus-LUNA statistic in the project inherits this.
  • The term-structure dimension is empty. Both abnormal-slope series have zero values, because the September contract file starts six weeks after the LUNA crisis and the FTX side never had a second leg.
  • Observations are treated as independent when they are not. Consecutive one-minute bars of a persistent, forward-filled series produce p-values of exactly zero and a t-statistic of 549. Step 17 computes the weights that would help and never applies them.
  • The classifier is circular. Two real events, expanded to 200 rows by adding noise to their own labels, then classified perfectly. It measures the noise generator.
  • The declared estimation windows are a month longer than the data. The exported appendix table reports the declared dates, not the realised ones.
  • Cumulative impact sums annualised rates over minutes. The resulting −4,763,269 per cent is not a quantity with a meaning.
  • Steps 14 to 19 are unverified. The pinned risklabai commit no longer exists on GitHub, so those six files could not be executed and their outputs are described from the source only.
  • There are no tests. The tests/ tree holds placeholder files.
  • There is no config.toml. Every setting except max_uniqueness_events requires editing a step file.
