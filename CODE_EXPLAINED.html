ftx-crash: reading the code

What the project does, how its parts fit together, and what to check before trusting its results.

How to use this

Sections follow execution order. Each snippet comes from src/ftx_crash/ or scripts/. Coloured boxes mark design choices, traps, and known weaknesses. Every number in a Sample data box came from this project's code and parquet files. Where the code could not run, the page says so.

The process in plain English

The project compares the Terra/LUNA collapse in May 2022 with the FTX exchange failure in November. It measures the gap between futures and spot prices, called the basis, once per minute. It subtracts each crisis's calm-period average to get an abnormal basis, then tests whether the FTX gap was larger, more volatile, and longer-lasting. The results say yes to all three. Section 10 explains why that conclusion is not reliable as stated.

02The execution model — pipeline.py and config.py

The code began as one long Jupyter notebook. It was split into nineteen files, but kept the notebook's shared dictionary of names: every file can read names created by earlier files and add new ones.

def run_pipeline(context_overrides: dict[str, Any] | None = None) -> dict[str, Any]:
    """Run each step script in sorted filename order with a shared global context.

    Returns the final execution namespace (all globals produced by the steps).
    """
    config = ProjectConfig()
    context = build_execution_context(
        config=config, context_overrides=context_overrides
    )

    for step_path in sorted(config.steps_dir.glob("*.py")):
        context["__file__"] = str(step_path)
        source = step_path.read_text()
        exec(compile(source, str(step_path), "exec"), context)

    return context
In plain words

It finds every .py file in steps, sorts the filenames, and runs each file with the same dictionary of names. A value created in file 03 is still available when file 17 runs.

What it does

Input: an optional dictionary of overrides. Output: the final namespace, which holds every variable created by the nineteen files (roughly 200 keys). Role: the pipeline engine.

Why it is written this way

GUIDE_src.md calls for notebook parity: the converted code should stay close enough to the original notebook for side-by-side comparison. The shared exec namespace preserves that behaviour, including its bad parts.

Trap

Because the files share one namespace, an import in file 01 can supply np to file 08. A tool checking one file at a time may delete that import as "unused". The run then fails later. That happened here; see Fixes applied.

Trap

The order is sorted filename order, not the split-map order. It works as intended because filenames use two-digit prefixes. 20_extra.py runs last; 9_extra.py runs after 19_... because "9" sorts after "1".

build_execution_context — makes the folders and seeds the namespace

def build_execution_context(
    config: ProjectConfig,
    context_overrides: dict[str, Any] | None = None,
) -> dict[str, Any]:
    """Build the shared global namespace used when executing step scripts."""
    config.processed_data_dir.mkdir(parents=True, exist_ok=True)
    config.figures_dir.mkdir(parents=True, exist_ok=True)
    config.tables_dir.mkdir(parents=True, exist_ok=True)

    overrides = dict(context_overrides or {})
    smoke_test_mode = bool(overrides.get("SMOKE_TEST_MODE", False))

    context: dict[str, Any] = {
        "__name__": "__main__",
        "PROJECT_ROOT": config.project_root,
        ...
        "OVERRIDES": overrides,
        "SMOKE_TEST_MODE": smoke_test_mode,
    }
    context.update(overrides)
    return context
What it does

Input: a ProjectConfig and optional overrides. Output: a dictionary with six paths and the override dictionary. Role: tells each step where files live.

Why paths are derived, not hard-coded

ProjectConfig.project_root is Path(__file__).resolve().parents[2]. Since the file is at src/ftx_crash/config.py, two levels up is the project root. All other paths start there, so the run works from any working directory.

The weakness, stated honestly

context.update(overrides) writes every override into the shared namespace. An override named data or plt would replace the panel or the plotting library without warning. The code has no allowed-key list or validation.

The BITO file has 29,627 one-minute bars over three months; the Bitcoin file has one bar for every minute. Step 06 repeats each BITO price until the next print, including overnight and weekend periods. The FTX "futures" series is therefore a step function, not a continuously observed price.

The conversion script, not the analysis, sets the date filters. Bitcoin spot starts on 2022-04-01 and BITO on 2022-10-01, but step 04 declares estimation windows beginning on 2022-03-01 and 2022-09-01. The data silently shortens those windows. See Edge cases.

05The basis and the panel — steps 05 and 06

calculate_basis — annualised gap between futures and spot

def calculate_basis(futures_price, spot_price, days_to_maturity):
    """Annualized futures basis in percent: ((F - S) / S) * (365 / T) * 100.

    Parameters
    ----------
    futures_price, spot_price
        Price series (aligned index).
    days_to_maturity
        Calendar days until contract expiry; floored at 1 to avoid division by zero.
    """
    days_to_expiry = np.maximum(days_to_maturity, 1)
    return ((futures_price - spot_price) / spot_price) * (365 / days_to_expiry) * 100
In plain words

Measure the futures price above or below the spot price, then express that gap as a yearly percentage.

What it does

Input: two aligned price series and calendar days to expiry. Output: a series of annualised percentages. Role: the study's main measurement; later steps use its output.

The formula

$$b_t \;=\; \frac{F_t - S_t}{S_t}\;\times\;\frac{365}{\max(T_t,\,1)}\;\times\;100$$

$b_t$ is the annualised basis at minute $t$; $F_t$ is the futures price; $S_t$ is the spot price; and $T_t$ is the whole number of calendar days from minute $t$ to expiry. $\max(\cdot,1)$ prevents division by zero on and after expiry. The factor $365$ turns a gap earned over $T_t$ days into a yearly rate, and $100$ converts a fraction to per cent.

Sample data

spot   S = 30191.82
futures F = 30824.00
expiry     2022-06-24
days    T = 45

16.983680   <- 2.09% gap over 45 days,
               annualised to about 17%

(30824.00 − 30191.82) / 30191.82 = 0.020939; 0.020939 × 365/45 × 100 = 16.9837.

06Abnormal basis and persistence — steps 07 and 08

Step 07 — subtract the calm-period average

luna_est_data = data.loc[luna_estimation_start:luna_estimation_end]

The formula

$$\bar b^{\,\text{est}} \;=\; \frac{1}{N_{\text{est}}}\sum_{t \in \text{estimation}} b_t \qquad\qquad a_t \;=\; b_t - \bar b^{\,\text{est}}$$

$b_t$ is the annualised basis at minute $t$. $\bar b^{\,\text{est}}$ is its average in the estimation window, and $N_{\text{est}}$ is that window's number of minutes. $a_t$ is the abnormal basis: the difference from the pre-crisis average. This event-study residual uses a constant average, not a market model.

Why this is free of look-ahead bias

The benchmark comes from luna_est_data, which ends on 8 May, and is applied to a crisis starting 9 May. No crisis observation affects it. This is the project's clearest example of correct timing.

The weakness, stated honestly

The negative "normal basis" of −524.62 per cent is not a market fact. It is the average of the BITO-versus-Bitcoin error described in section 05. Subtracting it removes the constant part but not the part that changes with days-to-expiry.

calculate_half_life — how fast the dislocation faded

# The panel built in step 06 is 1-minute data, so an AR(1) fitted on consecutive
# rows gives a half-life counted in bars (minutes). Downstream steps print the
# half-life in hours and divide by 24 for days, so convert here.
BARS_PER_HOUR = 60


def calculate_half_life(series, bars_per_hour: float = BARS_PER_HOUR) -> float:
    clean_series = series.dropna()
    if len(clean_series) < 10:
        return np.nan

    y = clean_series.values[1:]
    y_lag = clean_series.values[:-1]

    # OLS estimate of rho (no intercept since abnormal basis is demeaned)
    rho = np.sum(y * y_lag) / np.sum(y_lag**2)

    # Handle edge cases
    if rho >= 1:  # Non-stationary (unit root or explosive)
        return np.inf
    elif rho <= 0:  # Negative autocorrelation (oscillatory)
        return np.inf  # Half-life undefined for negative rho

    half_life_bars = -np.log(2) / np.log(rho)
    return half_life_bars / bars_per_hour
In plain words

Measure how much each minute's dislocation carries into the next, then report how long it takes to fall by half.

What it does

Input: a post-crisis abnormal-basis series on the one-minute grid. Output: the half-life in hours, or infinity when the fitted series does not decay. Role: measures persistence, one part of the comparison.

The formula

The code fits a first-order autoregression through zero: the current value depends on the previous value, with no constant term.

$$a_t \;=\; \rho\, a_{t-1} + \varepsilon_t$$

Its least-squares estimate is the cross-product of current and previous values divided by the sum of squared previous values:

$$\hat\rho \;=\; \frac{\sum_{t=2}^{N} a_t\,a_{t-1}}{\sum_{t=2}^{N} a_{t-1}^{2}}$$

After $k$ minutes, the expected level is $\rho^{k} a_t$. Set that level to half and take logarithms to get the half-life in bars. The code divides by 60 to get hours:

$$H \;=\; \frac{-\ln 2}{\ln \hat\rho}\;\Big/\;60$$

$a_t$ is the abnormal basis at minute $t$. $\varepsilon_t$ is the part the model does not explain. $\hat\rho$ is the estimated carry-over; a decaying series has a value between 0 and 1. $N$ is the number of post-crisis minutes. $H$ is the half-life in hours. The 60 is BARS_PER_HOUR, the number of one-minute bars in an hour.

Sample data
in — post-crisis abnormal basis 
LUNA: 2022-05-21 -> 2022-06-30, 1-min
FTX:  2022-11-20 -> 2022-12-31, 1-min
out — half-life 
LUNA:   5.8 hours  (0.2 days)
FTX:    inf        <- rho fell outside (0, 1)

The FTX result is infinity, not a large number. Steps 10 and 12 therefore print infx in each "Ratio (FTX/LUNA)" cell.

Why there is no intercept

The series already has its estimation-window average removed, so the code treats it as centred on zero and omits the intercept.

The weakness, stated honestly

This is valid only if the post-crisis average is also zero. It was centred using a different window, so that need not hold. A non-zero mean pushes $\hat\rho$ upward and lengthens the half-life. Including an intercept would be more defensible.

Trap

Returning np.inf for both $\hat\rho \ge 1$ and $\hat\rho \le 0$ hides two different cases: "never decays" and "changes sign every bar". The output inf does not distinguish them.

def cohens_d(x1, x2):
    """Calculate Cohen's d effect size."""
    n1, n2 = len(x1), len(x2)
    var1, var2 = np.var(x1, ddof=1), np.var(x2, ddof=1)
    pooled_std = np.sqrt(((n1 - 1) * var1 + (n2 - 1) * var2) / (n1 + n2 - 2))
    return (np.mean(x1) - np.mean(x2)) / pooled_std


basis_cohens_d = cohens_d(ftx_ab_basis, luna_ab_basis)
did_estimate = ftx_avg_abnormal_basis - luna_avg_abnormal_basis
In plain words

Ask whether the averages differ (t-test), whether the distributions differ (Mann-Whitney test), and how large the gap is relative to the spread (Cohen's d).

The formula

Welch's t-statistic, which allows the groups to have different spreads:

$$t \;=\; \frac{\bar x_1-\bar x_2}{\sqrt{\dfrac{s_1^{2}}{n_1}+\dfrac{s_2^{2}}{n_2}}}$$

Cohen's d, the gap measured in pooled standard deviations:

$$d \;=\; \frac{\bar x_1-\bar x_2}{s_p}, \qquad s_p \;=\; \sqrt{\frac{(n_1-1)s_1^{2}+(n_2-1)s_2^{2}}{n_1+n_2-2}}$$

The difference-in-differences estimator is just the gap between the two average abnormal bases here:

$$\delta_{\text{DiD}} \;=\; \bar a^{\,\text{FTX}} - \bar a^{\,\text{LUNA}}$$

$\bar x_i$ is group $i$'s mean, $s_i^{2}$ its sample variance, and $n_i$ its size. $s_p$ is the pooled standard deviation. $\bar a^{\,\text{FTX}}$ and $\bar a^{\,\text{LUNA}}$ are the two crisis-window average abnormal bases. The cohens_d call uses group 1 for FTX and group 2 for LUNA, so $d$ is negative.

In plain words

Take the first six minutes of each crisis, reduce them to four numbers, add random noise to create training rows, and train a random forest to separate the crises.

What it does

Input: the crisis-window slice of data. Output: four features per crisis, 100 noisy copies of each, a fitted RandomForestClassifier, and a feature-importance table. Role: supports the project's "early warning" claim.

The formula

Each synthetic sample equals the real feature plus normally distributed noise scaled to that feature's size:

$$x^{(i)}_j \;=\; x_j \;+\; \varepsilon^{(i)}_j, \qquad \varepsilon^{(i)}_j \sim \mathcal{N}\!\left(0,\;\bigl(\sigma\,|x_j| + \epsilon_0\bigr)^{2}\right)$$

Step 15 — the CUSUM filter

The formula

The symmetric cumulative-sum (CUSUM) filter keeps an upward and a downward total. It records an event when either crosses a threshold, then resets both:

$$S^{+}_t=\max\bigl(0,\;S^{+}_{t-1}+\Delta y_t\bigr), \qquad S^{-}_t=\min\bigl(0,\;S^{-}_{t-1}+\Delta y_t\bigr)$$

It records an event at time $t$ when $S^{+}_t \ge h_t$ or $S^{-}_t \le -h_t$, then resets the total that crossed the threshold.

$\Delta y_t$ is the price change from $t-1$ to $t$. $S^{+}$ collects upward moves and $S^{-}$ collects downward moves. $h_t$ is the changing threshold. daily_volatility_with_log_returns(prices, span=100) estimates rolling volatility as a fraction; multiplying by price converts it to currency units.

Why the timezone is stripped and put back

Lines 6 to 12 of step 15 remove the UTC label before calling RiskLabAI and restore it afterwards. The library does not handle timezone-aware indexes, so the code works around that limitation. It assumes the naive timestamps were UTC, which they were.

Step 16 — fractional differentiation

The formula

Ordinary differencing subtracts the previous value and removes the level. Fractional differencing uses a non-integer order, which removes the trend more gradually:

$$\tilde y_t \;=\; \sum_{k=0}^{K} \omega_k \, y_{t-k}, \qquad \omega_0 = 1, \qquad \omega_k \;=\; -\,\omega_{k-1}\,\frac{d-k+1}{k}$$

$y_t$ is the original series and $\tilde y_t$ the differenced series. $d$ is the differencing degree: $d=0$ leaves the series unchanged; $d=1$ is ordinary first differencing. $\omega_k$ is the weight on the value $k$ steps back. $K$ is where the weights are cut off. The code searches for the smallest $d$ that passes the augmented Dickey-Fuller stationarity test at five per cent, preserving the most memory.

Why the series is shifted before differencing

The RiskLabAI routine takes logarithms, which require positive inputs. Because the basis becomes negative, lines 19 and 20 first add abs(global_min) + 100 to every value. The comment calls the buffer 100 per cent.

Trap

Step 18 reuses shift_val, calibrated on the raw basis, for the abnormal basis. Their minima differ, so the shift may not make the abnormal series positive. Step 18's comment only says "use the SAME shift_val".

Step 17 — sample uniqueness weights

The formula

Two observations covering the same time carry overlapping information. Concurrency counts how many observations are active at each instant. An observation's weight is the average reciprocal concurrency over its lifetime:

$$c_t \;=\; \sum_{i=1}^{N} \mathbf{1}_{\{t \in [t_{i,0},\, t_{i,1}]\}}, \qquad u_i \;=\; \frac{1}{|I_i|}\sum_{t \in I_i} \frac{1}{c_t}$$

$N$ is the number of events. $[t_{i,0}, t_{i,1}]$ is event $i$'s interval, from its observation minute to contract expiry. $\mathbf{1}_{\{\cdot\}}$ is 1 when its condition holds and 0 otherwise, so $c_t$ counts active events at time $t$. $I_i$ is event $i$'s set of time steps and $|I_i|$ its size. $u_i$ lies between 0 and 1: near 1 when the event is alone and near 0 when it overlaps heavily. The weights are then rescaled to sum to $N$.

Why the event count is capped

create_indicator_matrix builds one row per minute and one column per event. At 1,000 events over roughly 70,000 minutes, it already uses about 70 megabytes of unsigned bytes. Without the max_uniqueness_events = 1000 cap and the sampling in reduce_event_count, the full 70,000 events would need a matrix around seventy times larger.

The weakness, stated honestly

The weights are computed but never used in step 09. Step 17 prints a weighted mean beside the unweighted mean and stops. The headline p-values are still unweighted.

Step 18 — the backdoor regression

The formula

$$\tilde a_t \;=\; \beta_0 \;+\; \beta_1 \, D_t \;+\; \beta_2 \, \sigma_t \;+\; \beta_3 \ln P_t \;+\; u_t$$

$\tilde a_t$ is the fractionally differenced abnormal basis. $D_t$ is the crisis indicator: 0 for LUNA and 1 for FTX. $\sigma_t$ is the rolling 24-bar return standard deviation multiplied by $\sqrt{24}$. $\ln P_t$ is the natural log of Bitcoin's price. $u_t$ is the residual. $\beta_1$ is the reported FTX effect after holding volatility and price level fixed. Here, "backdoor adjustment" means controlling for the market regime.

Trap

The volatility control multiplies by $\sqrt{24}$, which is correct only for hourly data. This panel is one-minute data, so the scale is wrong. The same scale is absorbed by $\beta_2$, leaving $\beta_1$ unchanged, but the reported $\beta_2$ is not in the stated units.

Step 19 — synthetic robustness

The formula

The simulated market uses a Heston stochastic-volatility model with Merton jumps and two regimes that switch through a Markov chain:

$$dS_t = \mu S_t\,dt + \sqrt{v_t}\,S_t\,dW^{S}_t + S_t\,dJ_t$$

$$dv_t = \kappa\,(\theta - v_t)\,dt + \xi\sqrt{v_t}\,dW^{v}_t, \qquad \mathrm{corr}\bigl(dW^{S}_t, dW^{v}_t\bigr) = \rho$$

$S_t$ is the simulated price and $v_t$ its instantaneous variance. $\mu$ is the drift, calibrated from each crisis's mean return. $\kappa$ controls how quickly variance returns to its long-run level $\theta$, set to the crisis's squared annualised volatility. $\xi$ is the volatility of variance. $\rho$ is the correlation between the random drivers, set to $-0.7$ and $-0.8$. $dJ_t$ is a jump term firing at rate $\lambda$, with mean size $m$ and variance $v$. The transition matrix is $\begin{pmatrix}0.95 & 0.05\\ 0.05 & 0.95\end{pmatrix}$, so each step has a five per cent chance of switching regime.

Why there is a fallback

The generation call is inside try. If RiskLabAI raises an error, the code prints it and falls back to bootstrap resampling of the real crisis returns. The run continues and the error is visible, but the final conclusion does not say which path produced the numbers.

Trap

The fallback calls np.random.random() without its own seed. It inherits the random state left by step 13, so its results are reproducible only by accident.

10What the numbers actually mean

The central problem, stated first

The FTX side does not measure a futures basis. The formula $(F-S)/S$ requires $F$ and $S$ to be prices for the same underlying quantity. Here, $F$ is the BITO exchange-traded fund share price (about \$2.66), while $S$ is the price of one Bitcoin (about \$17,663). One BITO share is not one Bitcoin. Thus $(F-S)/S$ is about $-1$ every minute, and the "annualised basis" becomes $-100 \times 365/T$, which follows the days-to-expiry calendar.

What would make the comparison sound

Three changes matter most. First, compare like with like: use the Binance December 2022 quarterly Bitcoin contract against Bitcoin spot for the FTX window, as the LUNA window does with the June contract. Its pre-expiry numbers are meaningful: the mean basis is about 2.7 per cent annualised and falls to −64 per cent at the worst minute of the May crisis. "Why is the FTX half-life infinite?"The estimated one-lag coefficient fell outside 0 to 1, so the function returns np.inf instead of a negative or undefined half-life.
"What happens if I change the crisis window in step 04?"Everything downstream changes: the benchmark, both abnormal series, all three tests, classifier features, and causal regression. Nothing is cached, so rerun the pipeline.
"Why does the FTX basis barely move minute to minute?"It is not measuring a basis. A \$2.66 exchange-traded fund share is compared with a \$17,663 Bitcoin, so the ratio stays near −1 and follows the days-to-expiry calendar. See section 10.
"How long does a full run take?"Steps 01 to 13 take a few minutes on the bundled data. Steps 15 and 17 are slower: the CUSUM filter walks 260,428 rows in Python, and the uniqueness matrix is about 70 megabytes per crisis. Steps 14 to 19 could not be timed because the dependency will not install.
"Why is --smoke there if it does nothing?"It is unfinished support for shorter runs. SMOKE_OVERRIDES is empty, so the flag has no effect. Adding {"max_uniqueness_events": 50} would give it one.
"Which tables are trustworthy?"tab_appendix_event_timeline overstates the estimation windows. tab1, tab2, and tab4 are each written twice under similar names, in steps 06 to 13 and again in step 19. Only the LUNA columns use a correctly constructed basis.

18Limitations, stated honestly

  • The FTX basis is not a basis. Comparing a \$2.66 fund share with a \$17,663 Bitcoin makes the series follow days to expiry. Every FTX-versus-LUNA statistic inherits this error.
  • The term-structure dimension is empty. Both abnormal-slope series have zero values. The September contract starts six weeks after the LUNA crisis, and the FTX side has no second leg.
  • Observations are treated as independent when they are not. Consecutive one-minute bars from a persistent, forward-filled series produce p-values of exactly zero and a t-statistic of 549. Step 17 computes useful weights but never applies them.
  • The classifier is circular. Two real events are expanded to 200 rows by adding noise to their labels, then classified perfectly. It measures the noise generator.
  • The declared estimation windows are a month longer than the data. The appendix table reports declared dates, not realised ones.
  • Cumulative impact sums annualised rates over minutes. The resulting −4,763,269 per cent has no clear meaning.
  • Steps 14 to 19 are unverified. The pinned risklabai commit no longer exists on GitHub, so those six files could not run. Their outputs are described from the source only.
  • There are no tests. The tests/ tree holds placeholder files.
  • There is no config.toml. Every setting except max_uniqueness_events requires editing a step file.
